FRAME 05/05 · UX/UI DEV

UX/UI no desenvolvimento de interfaces

O momento em que decisões de design deixam de ser um arquivo do Figma e passam a ser HTML, CSS e JavaScript rodando de verdade.

UX e UI não são a mesma coisa

É comum tratar "UX/UI" como um único termo, mas eles respondem perguntas diferentes. UX (User Experience) pergunta: essa pessoa consegue atingir o objetivo dela usando este produto, de forma clara e sem frustração? UI (User Interface) pergunta: como essa tela específica deveria parecer e se comportar — cores, tipografia, espaçamento, estados de um botão? UX pensa no fluxo inteiro; UI desenha o que fica na tela em cada passo desse fluxo.

Do protótipo ao código

Depois que um fluxo passa pelas fases de Design Thinking e é validado com usuários, ele normalmente existe como um protótipo — em uma ferramenta como o Figma. A partir daí, alguém (ou a mesma pessoa) precisa traduzir aquele protótipo estático em uma interface real, funcional, escrita em HTML, CSS e JavaScript. Esse processo é chamado de handoff, e é onde boa parte dos problemas de usabilidade aparece: uma sombra, um espaçamento ou um estado de hover que existia no protótipo pode se perder na implementação se não houver comunicação clara entre quem desenhou e quem programou.

Design systems

Para reduzir essa perda entre design e código, times de produto costumam manter um design system: um conjunto documentado de cores, tipografia, espaçamentos e componentes reutilizáveis (botões, campos de formulário, cartões) que existe tanto no Figma quanto no código. Isso é, na prática, a heurística de "consistência e padrões" (frame anterior) aplicada em escala — cada botão se comporta da mesma forma porque vem da mesma origem.

Acessibilidade não é uma etapa final

Um erro comum é tratar acessibilidade como uma revisão de última hora, feita depois que a interface já está pronta. Na prática, boa parte das diretrizes WCAG (frame anterior) só funciona bem quando é decidida durante o desenvolvimento: usar elementos HTML semânticos (<button> em vez de uma <div> clicável), manter uma ordem lógica de navegação por teclado, garantir contraste de cor desde a escolha da paleta, e escrever texto alternativo para imagens que carreguem informação.

Prototipação também é código

Nem todo protótipo precisa nascer em uma ferramenta visual. Protótipos em HTML/CSS/JS — mesmo simples, como este próprio site — servem para testar comportamento real: como um menu se comporta ao encolher a tela, como um formulário reage a um erro de preenchimento, como o foco do teclado se move entre elementos. Esse tipo de teste só é totalmente confiável em código, porque é isso que a pessoa vai efetivamente usar no final.

Fechando o ciclo

IHC dá a base teórica; Design Thinking dá o processo; as heurísticas de Nielsen dão os critérios para avaliar o resultado; o WCAG garante que esse resultado funcione para o maior número possível de pessoas; e o desenvolvimento de interfaces é onde tudo isso, finalmente, vira algo que pode ser clicado, tocado e usado.
